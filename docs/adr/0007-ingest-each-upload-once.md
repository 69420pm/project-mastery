# Ingestion: process every upload once

> The map build: superseded by [ADR 0023](0023-knowledge-map-from-chapters.md), which builds the Knowledge map from Chapter units, each extracted once while its content is unchanged. Ingestion below is as #228 changed it: page batches, an Outline call and one pairing call.

**Context.** Grounded answers need citations down to the slide or page. Course PDFs in STEM are full of formulas, diagrams and scanned exams, which plain text extraction loses. Not every model accepts PDF files directly, but most current models accept images.

**Decision.** Ingest each upload once in a background workflow: render each page to an image, convert it with a vision model to markdown with LaTeX, split it into chunks that keep their page reference, embed the chunks into pgvector, and derive the Knowledge map. Every feature reuses this result.

The parse makes vision calls on the `ingest` task, one per batch of up to 5 pages, one structure call per Material for its Outline, and embedding calls on the `embed` task (see below). The structure call sees only the headings, the first characters of each page and the PDF outline, so no prompt carries the whole Material (#228).

- **One vision call per page batch.** It gets each page's number, image (a PDF page rendered to JPEG with a 2,000-pixel long edge from the stored file for that call and not kept, or the uploaded image itself) and, when the PDF has a text layer on the page, that text as a hint: it may be out of order and garbles formulas, so the image wins. It returns the batch's units: markdown in the source language with LaTeX formulas, a plot or drawing described in a `**Figure:**` blockquote, one of five labels (heading, content, exercise, solution, admin), the pages it spans, a heading's style, and whether the first and last unit continue across the batch's edges. Page furniture is not transcribed: running headers, footers, page numbers, logos, title pages, tables of contents, indexes and reference lists. Each page's result is stored, so a retried parse skips finished pages; a failed batch is read again page by page.
- **One structure call per Material.** With reasoning on, it proposes the Material's Outline of Chapters from its heading units, page starts and PDF outline, with the Material's language and its notation notes. Code checks each Chapter against the units and falls back to the PDF outline when the call fails.
- **Skipped and unreadable pages.** Code skips a slide overlay (a page whose text layer starts the next page's) and a blank render without a call. A page whose call still fails after its retries is stored `unreadable` with no units, the parse goes on, and the Materials page lists it. A reached Daily limit still fails the parse.
- **Steps.** A read step opens the PDF once and reads up to 20 pages, a few batch calls at a time, and starts no call after 150 seconds, so it ends within Vercel Hobby's 300-second limit. Every step sets the Material's heartbeat; a parse without one for 30 minutes counts as failed, so the Student can start it again.

- **Chunks in code.** Each unit is a chunk; a unit joins the one before only across a batch edge, when both flags say so and the labels match. Chunks are cut at every Chapter start, a Chapter's heading becomes a Markdown heading, and a chunk over 6,000 characters splits between paragraphs. Each chunk sits in its deepest Chapter. The Outline and the chunks are stored in one transaction. A Chapter is what the map build reads.

The non-admin chunks are then embedded as documents (`embedMany` on the `embed` task with Cohere's `search_document` input type, only chunks without a vector, in batches so a retry loses little); admin chunks are never searched or paired, so they get no vector. The parse ends with a pairing pass: every exercise chunk of the Course is paired with its solution chunk, or "no solution". Pairing runs on every parse and after every delete of a Material, and is recomputed for the whole Course, so upload order does not matter. One call on the `ingest` task, with reasoning on, sees every exercise and solution chunk of the Course with its Material, Chapter path and first 300 characters and names each exercise's solution; code drops ids it did not offer (#228). A Course with more than 400 such chunks is paired in runs of 400. A pass takes a request number first (`request_exercise_pairing`) and writes only while it is still the Course's latest request (`replace_exercise_solutions`), so of overlapping passes only the last writes.

Page images and figure pictures are not stored: a PDF stays the only copy of its pages. A figure is its description in the unit's Markdown. The starting model is `xiaomi/mimo-v2.6-flash`, a cheap vision model that reads page images (not PDF files) and lets whole scripts be parsed on the Gateway's monthly free credit; the task can move to a flash model in `src/lib/ai/models.ts` when real material needs it. Every call is recorded against the Student's Daily limit, and there is no page cap.

The Knowledge map, like parsing, processes each Chapter unit once: an update extracts only the units without a stored extraction of their current content, and retires the KCs whose chunks are gone ([ADR 0023](0023-knowledge-map-from-chapters.md)).

**Consequences.** Works with any vision model, so the ingestion model can change freely. Ingestion cost is paid once per upload, not per question. The exact conversion model is chosen by testing on real course materials. A Chat sends an attached Material raw, as an inline file, only with the message it is attached to (#251). Later turns carry the line "[Attached: <name>]", and the AI reaches the Material's chunks through `searchMaterials` once it is parsed, so a file is paid for once.
