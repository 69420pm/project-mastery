# Problem verification

**Context.** The tutor gets generated Problems (#183): variants of the Course's Exercises and new Problems, written by a small model. A Student trusts the numbers in a Problem and its solution, and a small model's arithmetic is not reliable. The model also cannot be its own judge: a second model reading the output would share its blind spots, double the cost of each stored Problem, and give a verdict nothing can check. ADR 0006 keeps AI cost in view, and the Student can flag a bad Problem, but a flag comes after the harm.

**Decision.** Numbers come from code, and a Problem is stored only when code has checked it. No second model judges it.

- **Program, not arithmetic.** The model writes the statement and solution with every number as a `{{variable}}` placeholder, plus a mathjs program (one assignment per line, units inline, at most 4,000 characters) and its final answers as a variable and a unit. A **math runner** evaluates the program and returns every assigned variable. The same runner serves the tutor's `compute` tool.
- **Failure rules.** A run fails when the program throws or runs over 2 s, assigns to a unit name (`m` would shadow the metre), gives a final answer that is not a quantity convertible to its declared unit (dividing by a unit drops it), or yields a non-finite value. Details are in `docs/agents/notes/mathjs-programs.md`.
- **Placeholders.** Code replaces each `{{variable}}` with the program's value at 4 significant figures and its unit, in the statement and the solution. A placeholder without a numeric value, or a `{{` left over, fails the draft. The stored final answers are the program's values, never the model's. The program is stored with the Problem, so the tutor labels the solution as computed by code, and a re-run reproduces the answers.
- **One retry.** A failed draft goes back once with the error. A second failure, or a model error, marks the Problem `failed` with the reason and its last program.
- **Separate process.** Each program runs in its own `node -e` process, with `--max-old-space-size=256` and a time limit, not in a worker thread. A worker's `resourceLimits` did not contain `sum(range(1, 1e8))`: V8's out-of-memory abort killed the whole Node process, the server with it. A process takes only itself down. The cost is about 0.4 s to start and load mathjs, and the 2 s limit counts from when mathjs has loaded.
- **A replaceable interface.** The runner is the one interface `run(program, declaredAnswers)` returning values or an error. A sandbox (a container, a Vercel Sandbox) can replace the process behind it without changing callers. Until then the process is a guard against runaway programs by honest mistakes, not a security boundary against hostile code: mathjs has no access to JavaScript, but the process runs with the server's permissions.
- **Quality stays human-read.** Code verifies that the numbers are consistent with the program, not that the Problem is a good one. The maintainer reads generated Problems by hand ([ADR 0012](0012-ai-observability-and-evals.md)); the `generate` smoke check checks that a queued run stores them. The Student's flag (`unclear`, `wrong`, `too_easy`, `off_topic`) removes a bad Problem from the pool.

**Consequences.** A stored Problem's numbers are consistent with its program, and a wrong formula in the program still passes: the check cannot tell a physically wrong model from a right one, so the solution's reasoning is as reliable as the model, and the flag is the remedy. A Problem without numbers has no program and no check beyond its shape; a solution of such a Problem is labelled so. Each program costs a process start, which is fine for a background workflow and for a tutor tool that runs a few times per reply. Whether a Vercel deployment can load mathjs from the runner's child process is not verified; if it cannot, the runner moves behind its interface to a sandbox. A calibrated quality judge for generated Problems is deferred to a later issue.
